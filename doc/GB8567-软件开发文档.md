## 1. 引言

### 1.1 编写目的

本文档依据 **GB/T 8567-2006《计算机软件文档编制规范》** 标准编制，旨在规范"智能奶茶档口系统"后端服务的开发过程，为开发人员、测试人员、运维人员及项目管理人员提供统一的技术参考。

本文档适用于以下人员：
- **开发人员**：理解系统架构、模块划分、接口规范、数据库设计
- **测试人员**：制定测试计划、设计测试用例、执行测试验证

- **项目管理人员**：跟踪开发进度、评估技术风险、制定资源计划

### 1.2 背景

#### 1.2.1 项目背景

随着新式茶饮市场快速发展，传统的人工点单、现金收银模式已无法满足高峰时段的效率需求。本项目旨在开发一套完整的智能奶茶档口管理系统，通过小程序、POS端、Web管理后台等多端协同，实现订单管理、支付处理、库存控制、会员营销等全业务流程数字化。

#### 1.2.2 项目目标

- **提升运营效率**：通过在线下单、自动打印、实时推送等功能，减少人工操作环节，提升单店日处理订单能力至500单以上
- **保障数据安全**：实现订单、支付、库存等核心数据的事务一致性，确保财务对账准确无误
- **支持业务扩展**：通过模块化设计和功能开关，支持预约单、会员积分、优惠券、配送等多种业务模式
- **降低运营成本**：采用混合云部署方案，核心服务部署在云端，热备服务部署在本地，兼顾性能与成本

## 2. 项目概述

### 2.1 项目简介

**智能奶茶档口系统后端**是基于 **FastAPI** 框架构建的异步RESTful API服务，为奶茶店提供完整的业务支撑能力。系统采用前后端分离架构，后端负责业务逻辑处理、数据持久化、第三方服务集成，前端包括顾客端小程序、商家端小程序、Web管理后台三个应用。

### 2.2 系统特性

#### 2.2.1 核心功能特性

1. **订单管理**
   - 用户在线下单（自取/配送）
   - 预约下单（指定取餐时间）
   - POS快速建单（现场收银）
   - 订单状态机流转（待支付→已支付→制作中→待取餐→已完成）
   - 订单取消与退款

2. **支付处理**
   - 微信支付JSAPI（小程序支付）
   - 微信支付Native（扫码支付）
   - 静态码支付匹配（自动/人工匹配）
   - 现金/POS刷卡支付
   - 支付回调处理与幂等保护
   - 支付流水记录

3. **库存管理**
   - 商品库存状态控制（在售/售罄）
   - 规格选项库存控制
   - 库存变更审计日志
   - 售罄后"想要"统计

4. **会员系统**
   - 会员积分累积（按消费杯数）
   - 满10杯自动发放优惠券
   - 优惠券核销与状态管理
   - 积分交易记录查询

5. **商家端功能**
   - WebSocket实时订单推送
   - 订单接单与状态更新
   - 数据看板（营业额/订单量/客单价）
   - 打印任务管理与重试

6. **系统管理**
   - 店铺信息配置
   - 营业时间管理
   - 配送范围管理
   - 功能开关控制
   - 运营数据统计

#### 2.2.2 技术特性

1. **高性能**
   - 异步I/O处理（asyncio + uvicorn）
   - 内存缓存（菜单数据，240秒TTL）
   - 数据库连接池（PgBouncer代理）
   - SQL查询优化（预加载、索引覆盖）

2. **高可用**
   - 混合云部署（云端主实例+本地热备）
   - 健康检查与自动重启
   - 数据库每日备份
   - 降级演练与应急预案

3. **安全性**
   - JWT令牌认证与授权
   - API限流防护（SlowAPI）
   - WAF统一入口（雷池）
   - 敏感数据脱敏
   - 审计日志记录

4. **可观测性**
   - Prometheus指标导出
   - Grafana可视化面板
   - 结构化日志（structlog）
   - 链路追踪（trace_id）
   - 黑盒网络质量监控

### 2.3 系统约束

#### 2.3.1 性能约束

| 接口类型 | SLO目标 | 说明 |
|---------|---------|------|
| `/menu` | P95 ≤ 40ms | 菜单查询，内存缓存命中率≥95% |
| `/orders` | P95 ≤ 200ms | 订单创建，含数据库写入 |
| `/payments/notify` | P95 ≤ 120ms | 支付回调处理 |
| WebSocket推送 | 延迟 ≤ 5s | 新订单推送到商家端 |
| 并发能力 | 100并发 | 当前架构安全并发线（0%错误率） |

#### 2.3.2 容量约束

| 资源类型 | 限制 | 说明 |
|---------|------|------|
| 数据库连接池 | 200 + 250溢出 | 总计450连接（支持100并发） |
| 单日订单量 | ≤ 10,000单 | 基于当前架构的容量规划 |
| 菜单商品数 | ≤ 100个 | 内存缓存容量限制 |
| WebSocket连接 | ≤ 50个 | 商家端同时在线数 |

#### 2.3.3 兼容性约束

- Python版本：≥ 3.11
- PostgreSQL版本：≥ 14
- Redis版本：≥ 5.0
- 小程序基础库版本：≥ 2.10.0

#### 4.2.2 分层职责

**API路由层（`app/api`）**
- 负责HTTP请求处理、参数解析、响应序列化
- 调用业务服务层，不直接操作数据库
- 处理认证、权限校验、限流
- 保持路由处理器轻量（<50行）

**业务服务层（`app/services`）**
- 实现核心业务逻辑
- 操作ORM模型，执行数据库事务
- 调用第三方服务（支付、打印等）
- 服务间通过依赖注入协作

**数据持久层（`app/models`）**
- SQLAlchemy ORM模型定义
- 数据库表结构映射
- 关系定义（一对多、多对多）
- 索引和约束声明

**工具层（`app/utils`）**
- 通用工具函数
- 可独立测试、无业务逻辑
- 可跨服务复用

### 4.3 技术选型

| 技术领域 | 选型 | 理由 |
|---------|------|------|
| Web框架 | FastAPI | 高性能、异步支持、自动文档、类型安全 |
| ORM | SQLAlchemy 2.0 | 异步支持、成熟稳定、社区活跃 |
| 数据库 | PostgreSQL 14 | 事务强一致、丰富索引、JSON支持 |
| 缓存 | Redis 5.0 | 高性能、数据结构丰富、Pub/Sub支持 |
| 任务队列 | Celery | 成熟的分布式任务队列、丰富的调度策略 |
| 日志 | Structlog | 结构化日志、便于解析和检索 |
| 监控 | Prometheus + Grafana | 业界标准、强大的查询语言、丰富的可视化 |

#### 4.4.1 混合云拓扑

```
           ┌─────────────────────────────────┐
           │         云端（公网）             │
           │                                 │
           │  ┌─────────┐      ┌──────────┐ │
           │  │雷池WAF  │──────│PostgreSQL │ │
           │  └────┬────┘      └──────────┘ │
           │       │                         │
           │       ▼                         │
           │  ┌─────────────────┐           │
           │  │  K3s Ingress    │           │
           │  └────┬────────────┘           │
           │       │                         │
           │  ┌────▼─────┐  ┌────────┐      │
           │  │ API Pod  │  │ Redis  │      │
           │  │ (2副本)  │──│        │      │
           │  └──────────┘  └────────┘      │
           └─────────────────────────────────┘
                     │
               VPN/专线 (WireGuard)
                     │
           ┌─────────▼─────────────────────┐
           │       家庭（内网）             │
           │                                │
           │  ┌──────────┐                 │
           │  │ K3s Agent│                 │
           │  └────┬─────┘                 │
           │       │                        │
           │  ┌────▼─────┐                 │
           │  │ API Pod  │                 │
           │  │ (1副本)  │                 │
           │  │ [热备]   │                 │
           │  └──────────┘                 │
           └────────────────────────────────┘
```

**说明**：
- **云端**：对外服务的主实例，处理所有流量
- **家庭**：热备实例，不对外暴露，保持同步运行
- **降级策略**：云端故障时，手动切换流量到家庭节点（或保持云端独活）

#### 4.4.2 容器化部署

**生产环境配置**（`docker-compose.prod.yml`）

```yaml
version: '3.8'

services:
  api:
    image: naicha-backend:${VERSION}
    environment:
      - APP_ENV=prod
      - DATABASE_URL=${DATABASE_URL}
      - CELERY_BROKER_URL=redis://redis:6379/0
    deploy:
      replicas: 2
      resources:
        limits:
          cpus: '2'
          memory: 2G
        reservations:
          cpus: '1'
          memory: 1G
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:8000/healthz"]
      interval: 30s
      timeout: 10s
      retries: 3

  worker:
    image: naicha-backend:${VERSION}
    command: celery -A app.workers.tasks worker --loglevel=info
    environment:
      - APP_ENV=prod
      - CELERY_BROKER_URL=redis://redis:6379/0

  beat:
    image: naicha-backend:${VERSION}
    command: celery -A app.workers.tasks beat --loglevel=info
    environment:
      - APP_ENV=prod
      - CELERY_BROKER_URL=redis://redis:6379/0

  redis:
    image: redis:7-alpine
    volumes:
      - redis-data:/data
    command: redis-server --appendonly yes

volumes:
  redis-data:
```
