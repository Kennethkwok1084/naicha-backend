| **PaymentService** | 支付回调处理、订单状态更新、支付记录 | Order、PaymentRecord、PrintJob、LoyaltyService | 🚨 事务内耦合积分/打印/通知 |

### 1.2 模块职责重叠问题

**问题 1: 库存管理职责分散**
- **现状:** `OrderService` 通过 `_load_products_with_groups` 使用 `SELECT ... FOR UPDATE` 锁定商品行,并基于 `stock_quantity` 同事务扣减; `InventoryService.restore_from_order_items` 负责回补库存并刷新 `inventory_status`
- **风险:** ✅ 已通过行级锁+`stock_quantity` 字段消除并发超卖,同时新增 `inventory_deduction_total`/`inventory_current_stock` 指标持续观测
- **证据:** `app/services/orders.py:152-170` 扣减后同步更新 gauge, `app/services/inventory.py:120-180` 回补库存也会回写指标
- **建议:** 保持现有实现,仅需在运营侧调优 `stock_quantity` 初始值

**问题 2: 幂等记录与游客会话共表**
- **现状:** `IdempotencyKey` 表同时存储订单幂等和游客会话
- **风险:** 逻辑耦合,且无行级锁保护,并发写入易冲突
- **证据:** `app/services/orders.py:338-382` 幂等插入使用 `ON CONFLICT DO NOTHING`
- **修复状态:** ✅ V3.0.1 已改用行级锁 + 轮询策略

**问题 3: 支付回调职责过重**
- **现状:** `PaymentService.handle_wechat_notification` 在单事务内处理支付记录、积分、打印、通知
- **风险:** 非核心步骤(打印入队、通知)失败会导致核心的支付状态更新回滚
- **证据:** `app/services/payments.py:63-260` 事务包含 `enqueue_print_job` 调用
- **修复状态:** ✅ V3.0.1 已拆分为事务内核心逻辑 + 事务外副作用

### 1.3 单点高耦合清单

| **耦合点** | **位置** | **风险等级** | **修复状态** |
|----------|---------|------------|------------|
| 支付回调 → 打印入队 | `payments.py:245-252` | 🚨 P0 | ✅ 已移到事务外 |

## 二、业务流程设计分析

### 2.1 下单链路 (`POST /api/v1/orders`)

#### 流程时序

```
客户端 → API网关 → FastAPI路由
   ↓
OrderService.create_order
   ├─ 1. 校验 Idempotency-Key (新: 行级锁 + 轮询)
   ├─ 2. 校验 guest_session_id
   ├─ 3. 加载商品/规格 (普通 SELECT,无锁)
   ├─ 4. 检查 inventory_status (TOCTOU 风险)
   ├─ 5. 计算价格、预约校验
   ├─ 6. INSERT Order + OrderItem
   ├─ 7. 更新幂等快照
   └─ 8. Commit 事务
```

#### 关键风险点

| **风险** | **描述** | **防护机制** | **状态** |
|---------|---------|------------|---------|
| **并发超卖** | `_load_products_with_groups` 使用 `SELECT ... FOR UPDATE` 锁定商品,同事务扣减 `stock_quantity` | ✅ 行级锁 + `inventory_deduction_total` 指标告警 | ✅ 已修复 (V3.0.2) |
| **幂等冲突** | 重复 Idempotency-Key 并发写入主键冲突 | ✅ 行级锁 + 轮询 | ✅ 已修复 |
| **预约超额** | 预约时段校验无锁 | ⚠️ 未明确 | ⚠️ 中危 |
| **重试攻击** | 恶意用户短时间大量重试不同 payload | ✅ Payload Hash 校验 | ✅ 有防护 |

#### 并发场景验证

- ✅ 新增 `tests/services/test_order_concurrency.py::test_concurrent_order_creation_respects_stock`
  - PostgreSQL 引擎下并发 20 次下单,仅首批 5 单能够成功获取行级锁,其余 15 单稳定返回 `OrderValidationError`
  - 测试同时断言最终 `stock_quantity` 归零且 `inventory_status` 自动标记为 `sold_out`
- ✅ 预约场景新增 `test_reservation_slot_capacity_enforced` 与 `test_cancel_reservation_releases_slot`,验证档期容量与释放流程

### 2.3 库存扣减与同步

#### 当前设计 (V3.0.2)

```
下单流程:
  OrderService._load_products_with_groups → SELECT ... FOR UPDATE 锁定商品行
  → 校验 stock_quantity → 扣减并更新 inventory_status → 记录 Prometheus 指标

后台回补:
  InventoryService.restore_from_order_items → 锁定商品 → 增加 stock_quantity
  → 当库存 >0 自动恢复 inventory_status=in_stock → 刷新指标
```

- 商品模型已具备 `stock_quantity` 列（`CheckConstraint >=0`），并在行级锁保护下扣减
- 预约场景增加 `reservation_slots` 表及 `orders.reservation_slot_id` 外键，按 `RESERVATION_SLOT_GRANULARITY_MINUTES` 粒度和 `RESERVATION_SLOT_CAPACITY` 限额预占档期

#### 观测与治理

- `inventory_deduction_total{result=success|insufficient|restored}`：跟踪扣减/补货/超卖尝试
- `inventory_current_stock{product_id}`：Gauge 反映最新库存
- `inventory_oversell_total{product_id}`：侦测所有被拒绝的超卖请求
- 并发覆盖：`tests/services/test_order_concurrency.py` + 预约容量测试确保超卖无法复现

### 2.4 打印通知链路

#### 流程时序

```
支付成功/POS 下单 → 创建 PrintJob → Celery 入队
   ↓
process_print_job (Worker 消费)
   ├─ 1. 更新状态 → processing
   ├─ 2. 调用打印机 HTTP Webhook
   ├─ 3a. 成功 → 状态 = completed
   └─ 3b. 失败 → 状态 = failed, retry_count++
```

```
定时恢复 (60s 一次):
  run_print_job_recovery
   ├─ 1. SELECT job WHERE status='failed' AND retry_count < max
   ├─ 2. 重新入队 process_print_job
```

#### 关键风险点

| **风险** | **描述** | **防护机制** | **状态** |
|---------|---------|------------|---------|
| **任务重复** | 支付并发创建多个 PrintJob | ✅ order_id 唯一约束 | ✅ 已修复 |
| **任务丢失** | Broker 宕机导致队列清空 | ⚠️ 需配置 Redis 持久化 | ⚠️ 中危 |
| **重试耗尽** | 打印机长期离线,任务永久放弃 | ⚠️ 指数退避 + 上限 3 次 | ⚠️ 中危 |
| **恢复重叠** | 多实例同时执行恢复任务 | ✅ 分布式锁 | ✅ 已修复 |

#### 打印成功率监控

### 2.5 商家端 WebSocket 广播

#### 架构设计

```
支付成功 → PaymentService → merchant_notifier.broadcast
   ↓
Redis PubSub (跨实例) → 所有 Worker 订阅
   ↓
本地 WebSocket 连接池 → send_json 推送
```

#### 关键风险点

| **风险** | **描述** | **降级方案** | **状态** |
|---------|---------|------------|---------|
| **Redis 不可用** | PubSub 失败,跨实例无法通知 | 退化为单机广播 | ✅ 有降级 |
| **消息丢失** | 商户网络瞬断,PubSub 无确认 | ⚠️ 连接恢复后推送近 5min 订单 | ⚠️ 不完善 |
| **连接泄漏** | WebSocket 异常断开未清理 | ✅ 心跳超时自动关闭 | ✅ 已修复 |

#### 心跳机制 (已实现)

**证据:** `app/api/routes/ws/__init__.py:73-97`
```python
async def heartbeat():
    while True:
        await asyncio.sleep(30)  # 每 30s ping
        elapsed = datetime.now(UTC) - last_pong
        if elapsed.total_seconds() > 35:  # 5s grace period
            await websocket.close(code=1011, reason="Heartbeat timeout")
```

### A1. 库存原子扣减 (行级锁方案)

```python
# app/services/orders.py:157 替换为:
async def _load_and_lock_products(
    self, items: list[OrderItemCreateSchema]
) -> dict[int, Product]:
    """加载商品并加行级锁,同时扣减库存"""
    product_ids = [item.product_id for item in items]
    
    stmt = (
        select(Product)
        .where(Product.product_id.in_(product_ids))
        .with_for_update()  # 关键: 行级锁
    )
    
    result = await self._session.execute(stmt)
    products = {p.product_id: p for p in result.scalars()}
    
    # 扣减库存
    for item in items:
        product = products.get(item.product_id)
        if not product:
            raise OrderValidationError(f"Product {item.product_id} not found")
        
        if product.stock_quantity < item.quantity:
            raise OrderValidationError(
                f"Product {item.product_id} insufficient stock: "
                f"required {item.quantity}, available {product.stock_quantity}"
            )
        
        product.stock_quantity -= item.quantity
        if product.stock_quantity == 0:
            product.inventory_status = 'sold_out'
    
    return products
```

```python
# tests/services/test_order_concurrent.py (新建)
import asyncio
import pytest
from app.services.orders import OrderService, OrderValidationError

@pytest.mark.asyncio
async def test_concurrent_order_prevents_oversell(model_test_engine):
    """150 并发下单同一商品,库存 10,应仅 10 个成功"""
    
    # 准备: 创建库存 10 的商品
    async with async_sessionmaker(model_test_engine)() as session:
        async with session.begin():
            product = Product(
                product_id=1,
                name="测试商品",
                base_price=10.00,
                stock_quantity=10,
                inventory_status='in_stock'
            )
            session.add(product)
    
    # 执行: 150 并发下单
    async def create_order(idx: int):
        async with async_sessionmaker(model_test_engine)() as session:
            service = OrderService(session, get_settings())
            try:
                async with session.begin():
                    await service.create_order(
                        payload=OrderCreateRequestSchema(
                            items=[OrderItemCreateSchema(
                                product_id=1,
                                quantity=1
                            )],
                            order_type='pickup'
                        ),
                        idempotency_key=f"test-{idx}",
                        user=None
                    )
                return 'success'
            except OrderValidationError as e:
                if 'insufficient stock' in str(e):
                    return 'stock_out'
                raise
    
    results = await asyncio.gather(
        *[create_order(i) for i in range(150)],
        return_exceptions=True
    )
    
    # 验证: 仅 10 个成功
    success_count = sum(1 for r in results if r == 'success')
    stock_out_count = sum(1 for r in results if r == 'stock_out')
    
    assert success_count == 10, f"Expected 10 success, got {success_count}"
    assert stock_out_count == 140, f"Expected 140 stock_out, got {stock_out_count}"
    
    # 验证: 数据库最终库存为 0
    async with async_sessionmaker(model_test_engine)() as session:
        product = await session.get(Product, 1)
        assert product.stock_quantity == 0
        assert product.inventory_status == 'sold_out'
```
