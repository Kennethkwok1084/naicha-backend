### 问题 2：缺少量化验收标准（中风险）

**现状分析**：
```
P0 任务描述：
✓ "完成核心接口压测" —— 但未定义"完成"标准
✓ "配置复核并调整至目标值" —— 但未列出"目标值"
✓ "告警规则联调" —— 但未明确"联调"范围
```

**问题**：
- 验收标准模糊 → 无法判断任务是否真正完成
- 容易出现"差不多完成了"的自我欺骗
- Go-Live 检查清单可能与实际交付不匹配

**优化建议**：为每个 P0 任务补充 **SMART 验收标准**

#### 示例改写：

**改写前**：
```markdown
- [ ] 完成核心接口压测（100/200/500 并发）并记录基线结果
```

**改写后**：
```markdown
- [ ] 完成核心接口压测并记录基线结果
  - 验收标准：
    - ✓ 压测覆盖：GET /menu, POST /orders, POST /payments/notify, WS /ws/merchant
    - ✓ 并发级别：100/200/500，每级别持续 30s
    - ✓ 基线记录：P50/P95/P99 延迟、QPS、错误率，记录在 doc/perf-baseline.md
    - ✓ SLO 达标：/menu P95≤40ms, /orders P95≤200ms, 支付回调 P95≤120ms
    - ✓ 瓶颈分析：识别 top3 慢查询并优化（pg_stat_statements）
```

**改写前**：
```markdown
- [ ] PgBouncer、Redis、Celery Worker 配置复核并调整至目标值
```

**改写后**：
```markdown
- [ ] PgBouncer、Redis、Celery Worker 配置优化
  - 验收标准：
    - ✓ PgBouncer: pool_mode=transaction, max_client_conn=200, default_pool_size=25
    - ✓ Redis: maxmemory=1GB, maxmemory-policy=allkeys-lru, timeout=300
    - ✓ Celery: worker_concurrency=4, task_acks_late=True, prefetch_multiplier=4
    - ✓ 压测验证：无连接池耗尽、无 OOM、任务延迟 P95≤5s
```

**改写前**：
```markdown
- [ ] Prometheus 指标埋点和 Grafana 面板扩展上线；告警规则联调
```

**改写后**：
```markdown
- [ ] Prometheus 指标埋点和 Grafana 面板上线
  - 验收标准：
    - ✓ 新增指标：order_create_total, payment_callback_latency_ms, menu_cache_hit_rate（共 8 个，见清单）
    - ✓ Grafana 面板：业务/性能/错误 3 类，共 12 个图表
    - ✓ 告警规则：/orders P95>250ms, 支付成功率<99%, 打印失败>5%（共 5 条）
    - ✓ 联调验证：手动触发告警，确认 Slack/邮件送达
```

## M6 风险应对手册

### 风险 1：压测发现性能瓶颈

**触发条件**：
- /menu P95 > 50ms（超出 SLO 25%）
- /orders P95 > 250ms（超出 SLO 25%）
- 数据库 CPU > 80% 或慢查询 > 10 个

**应对措施**：
1. **立即暂停压测**，防止生产影响（如共用数据库）
2. **分析瓶颈**：
   - 数据库：`SELECT * FROM pg_stat_statements ORDER BY total_time DESC LIMIT 10;`
   - 应用：查看 Prometheus `http_request_duration_seconds` P95
   - 网络：检查 WAF → 应用 → 数据库 各段延迟
3. **优化措施**（按优先级）：
   - [ ] 增加数据库索引（如缺失 `orders(status, created_at)`）
   - [ ] 优化 ORM 查询（消除 N+1，增加 `selectinload`）
   - [ ] 调整 PgBouncer 连接池（增加 `default_pool_size`）
   - [ ] 启用 Redis 缓存（扩展菜单缓存范围）
4. **回归验证**：优化后重新压测，确认 P95 降至 SLO 以下
5. **时间窗口**：Week1 预留 2 天优化时间，如仍未达标 → 升级决策（延期/降低 SLO）

**回退方案**：
- 如优化无效 → 上线时限制并发（Nginx `limit_req`）
- 如压测环境有问题 → 改为生产环境小流量验证

### 风险 2：K3s 混合云网络阻断

**触发条件**：
- 家庭节点 → 云端主节点 RTT > 200ms 持续 10min
- 家庭节点离线（kubectl get nodes 显示 NotReady）
- VPN/Frp 隧道断连

**应对措施**：
1. **立即降级为单云模式**：
   ```bash
   # 1. 删除家庭节点标签（防止调度）
   kubectl label nodes home-node-1 mode=standby --overwrite
   
   # 2. 驱逐家庭节点上的 Pod
   kubectl drain home-node-1 --ignore-daemonsets
   
   # 3. 扩容云端副本
   kubectl scale deployment naicha-api --replicas=3 -n production
   ```

2. **验证服务可用性**：
   ```bash
   curl -H "Host: api.example.com" https://<云端IP>/healthz
   kubectl get pods -n production -o wide  # 确认全在云端节点
   ```

3. **排查网络问题**：
   - 检查家庭路由器/防火墙
   - 检查 VPN 隧道状态
   - 联系运营商（如持续不稳定）

4. **恢复混合云模式**：
   ```bash
   # 网络恢复后
   kubectl uncordon home-node-1
   kubectl label nodes home-node-1 mode=active --overwrite
   kubectl scale deployment naicha-api --replicas=4  # 恢复原副本数
   ```

**时间窗口**：
- 检测 → 决策：≤5min（自动化脚本）
- 降级操作：≤10min
- 验证：≤5min

**文档位置**：`doc/runbook.md` § 混合云网络故障处理

```

**时间窗口**：
- 监控检测 → 决策：≤10min
- 回退操作：≤5min
- 验证：≤5min

**文档位置**：`doc/runbook.md` § 支付服务降级流程
```

1. 明确触发条件（可量化、可监控）
