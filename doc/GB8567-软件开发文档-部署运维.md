# 智能奶茶档口系统后端软件开发文档（完结篇）

## 10. 部署方案

### 10.1 部署架构

#### 10.1.1 混合云拓扑

本系统采用**混合云部署架构**，实现成本与可用性的平衡：

```
┌──────────────────────────────────────────────────────────┐
│                      云端（阿里云）                       │
│                                                          │
│  ┌──────────────┐                                       │
│  │  雷池WAF     │  ←── 公网流量入口（HTTPS）             │
│  └──────┬───────┘                                       │
│         │                                                │
│  ┌──────▼──────────────────────────────┐               │
│  │  K3s Ingress (Nginx)               │               │
│  │  - 路由规则                         │               │
│  │  - SSL终止                          │               │
│  │  - 健康检查                         │               │
│  └──────┬──────────────────────────────┘               │
│         │                                                │
│  ┌──────▼──────────┐   ┌──────────────┐               │
│  │  API Pod 1      │   │  PostgreSQL  │               │
│  │  (FastAPI)      │──→│  14.x        │               │
│  │  资源: 2C/2G    │   │  (主库)      │               │
│  └─────────────────┘   └──────────────┘               │
│  ┌─────────────────┐   ┌──────────────┐               │
│  │  API Pod 2      │   │  Redis 7.x   │               │
│  │  (FastAPI)      │──→│  (缓存/队列) │               │
│  │  资源: 2C/2G    │   └──────────────┘               │
│  └─────────────────┘   ┌──────────────┐               │
│  ┌─────────────────┐   │  PgBouncer   │               │
│  │  Worker Pod     │   │  (连接池)    │               │
│  │  (Celery)       │   └──────────────┘               │
│  └─────────────────┘                                   │
│  ┌─────────────────┐                                   │
│  │  Beat Pod       │                                   │
│  │  (Celery)       │                                   │
│  └─────────────────┘                                   │
└──────────────────────────────────────────────────────────┘
                         │
                   VPN专线 (WireGuard)
                         │
┌────────────────────────▼─────────────────────────────────┐
│                      家庭（内网）                         │
│                                                          │
│  ┌──────────────────────────────────┐                  │
│  │  K3s Agent Node                  │                  │
│  └──────┬───────────────────────────┘                  │
│         │                                                │
│  ┌──────▼──────────┐                                   │
│  │  API Pod 3      │  ←── 热备实例（不对外）           │
│  │  (FastAPI)      │      仅用于灾备演练                │
│  │  资源: 1C/1G    │                                   │
│  └─────────────────┘                                   │
└──────────────────────────────────────────────────────────┘
```

**设计要点**：
1. **主在云端**：所有流量由云端处理，保证低延迟
2. **热备在家**：家庭节点保持热备状态，可用于应急切换
3. **数据集中**：数据库和Redis都在云端，避免数据同步问题
4. **弹性扩展**：云端可随时增加Pod副本数应对流量高峰

#### 10.1.2 资源规划

**云端资源配置**：

| 组件 | 规格 | 副本数 | 说明 |
|------|------|--------|------|
| API Pod | 2C/2G | 2 | 主服务实例 |
| Worker Pod | 1C/1G | 1 | 后台任务处理 |
| Beat Pod | 0.5C/512M | 1 | 定时任务调度 |
| PostgreSQL | 4C/8G | 1 | 主数据库 |
| Redis | 2C/2G | 1 | 缓存/消息队列 |
| PgBouncer | 1C/1G | 1 | 连接池代理 |

**家庭资源配置**：

| 组件 | 规格 | 副本数 | 说明 |
|------|------|--------|------|
| API Pod | 1C/1G | 1 | 热备实例 |

**存储需求**：

| 类型 | 容量 | 说明 |
|------|------|------|
| PostgreSQL数据 | 20GB | 预估50万订单 |
| 数据库备份 | 50GB | 保留30天备份 |
| Redis持久化 | 5GB | AOF持久化 |
| 日志存储 | 10GB | 保留7天日志 |

### 10.2 Docker部署

#### 10.2.1 Dockerfile

```dockerfile
# Dockerfile
FROM python:3.11-slim

WORKDIR /app

# 安装系统依赖
RUN apt-get update && apt-get install -y \
    gcc \
    postgresql-client \
    && rm -rf /var/lib/apt/lists/*

# 复制依赖文件
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# 复制应用代码
COPY . .

# 创建非root用户
RUN useradd -m -u 1000 appuser && \
    chown -R appuser:appuser /app
USER appuser

# 健康检查
HEALTHCHECK --interval=30s --timeout=10s --start-period=30s --retries=3 \
    CMD curl -f http://localhost:8000/healthz || exit 1

# 暴露端口
EXPOSE 8000

# 启动命令（可被docker-compose覆盖）
CMD ["uvicorn", "app.main:app", "--host", "0.0.0.0", "--port", "8000"]
```

#### 10.2.2 docker-compose.yml（生产环境）

```yaml
version: '3.8'

services:
  postgres:
    image: postgres:14-alpine
    environment:
      POSTGRES_DB: naicha
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - postgres-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER}"]
      interval: 10s
      timeout: 5s
      retries: 5
    restart: unless-stopped

  pgbouncer:
    image: edoburu/pgbouncer:1.18.0
    environment:
      DATABASE_URL: postgres://${DB_USER}:${DB_PASSWORD}@postgres:5432/naicha
      POOL_MODE: transaction
      MAX_CLIENT_CONN: 500
      DEFAULT_POOL_SIZE: 20
    depends_on:
      postgres:
        condition: service_healthy
    restart: unless-stopped

  redis:
    image: redis:7-alpine
    command: redis-server --appendonly yes
    volumes:
      - redis-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 10s
      timeout: 3s
      retries: 5
    restart: unless-stopped

  api:
    image: naicha-backend:${VERSION:-latest}
    command: gunicorn app.main:app \
      --worker-class uvicorn.workers.UvicornWorker \
      --workers 4 \
      --bind 0.0.0.0:8000 \
      --timeout 120 \
      --access-logfile - \
      --error-logfile -
    environment:
      APP_ENV: prod
      DATABASE_URL: postgresql+asyncpg://${DB_USER}:${DB_PASSWORD}@postgres:5432/naicha
      DATABASE_PROXY_URL: postgresql+asyncpg://${DB_USER}:${DB_PASSWORD}@pgbouncer:6432/naicha
      CELERY_BROKER_URL: redis://redis:6379/0
      WS_BROADCAST_URL: redis://redis:6379/0
      SECRET_KEY: ${SECRET_KEY}
    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    deploy:
      replicas: 2
      resources:
        limits:
          cpus: '2'
          memory: 2G
        reservations:
          cpus: '1'
          memory: 1G
    restart: unless-stopped

  worker:
    image: naicha-backend:${VERSION:-latest}
    command: celery -A app.workers.tasks worker \
      --loglevel=info \
      --concurrency=4
    environment:
      APP_ENV: prod
      DATABASE_URL: postgresql+asyncpg://${DB_USER}:${DB_PASSWORD}@postgres:5432/naicha
      DATABASE_PROXY_URL: postgresql+asyncpg://${DB_USER}:${DB_PASSWORD}@pgbouncer:6432/naicha
      CELERY_BROKER_URL: redis://redis:6379/0

    depends_on:
      postgres:
        condition: service_healthy
      redis:
        condition: service_healthy
    restart: unless-stopped

  beat:
    image: naicha-backend:${VERSION:-latest}
    command: celery -A app.workers.tasks beat \
      --loglevel=info
    environment:
      APP_ENV: prod
      DATABASE_URL: postgresql+asyncpg://${DB_USER}:${DB_PASSWORD}@postgres:5432/naicha
      CELERY_BROKER_URL: redis://redis:6379/0
      SECRET_KEY: ${SECRET_KEY}
    depends_on:
      redis:
        condition: service_healthy
    restart: unless-stopped

volumes:
  postgres-data:
  redis-data:
```

#### 10.2.3 部署流程

```bash
# 1. 构建镜像
docker build -t naicha-backend:v3.0.1 .

# 2. 推送到私有仓库
docker tag naicha-backend:v3.0.1 registry.example.com/naicha-backend:v3.0.1
docker push registry.example.com/naicha-backend:v3.0.1

# 3. 配置环境变量
cat > .env.prod <<EOF
VERSION=v3.0.1
DB_USER=naicha_prod
DB_PASSWORD=$(openssl rand -base64 32)
SECRET_KEY=$(openssl rand -base64 64)
EOF

# 4. 启动服务
docker-compose -f docker-compose.prod.yml up -d

# 5. 执行数据库迁移
docker-compose exec api alembic upgrade head

# 6. 验证服务
curl http://localhost:8000/healthz
```

#### 11.1.1 Prometheus监控指标

**业务指标**：

```python
# 订单创建计数
order_create_total = Counter(

payment_callback_latency_ms = Histogram(
```

#### 11.1.3 告警规则

```yaml
# prometheus-rules.yaml
groups:
- name: naicha-api-alerts
  interval: 30s
  rules:
  # API成功率低于99%
  - alert: HighAPIErrorRate
    expr: |
      rate(http_requests_total{status=~"5.."}[5m]) 
      / rate(http_requests_total[5m]) > 0.01
    for: 5m
    labels:
      severity: critical
    annotations:
      summary: "API错误率过高"
      description: "最近5分钟API 5xx错误率 {{ $value | humanizePercentage }}"

  # 支付回调延迟过高
  - alert: HighPaymentCallbackLatency
    expr: |
      histogram_quantile(0.95,
        rate(payment_callback_latency_ms_bucket[5m])
      ) > 200
    for: 5m
    labels:
      severity: warning
    annotations:
      summary: "支付回调延迟过高"
      description: "P95延迟 {{ $value }}ms，超过200ms阈值"

  # 数据库连接池耗尽
  - alert: DatabasePoolExhausted
    expr: |
      pg_stat_database_numbackends / 
      pg_settings_max_connections > 0.8
    for: 2m
    labels:
      severity: critical
    annotations:
      summary: "数据库连接池即将耗尽"
      description: "当前使用率 {{ $value | humanizePercentage }}"

  # 打印任务失败率过高
  - alert: HighPrintJobFailureRate
    expr: |
      rate(print_job_total{result="failed"}[10m]) 
      / rate(print_job_total[10m]) > 0.05
    for: 10m
    labels:
      severity: warning
    annotations:
      summary: "打印任务失败率过高"
      description: "最近10分钟失败率 {{ $value | humanizePercentage }}"

  # 家→云网络延迟过高
  - alert: HighNetworkLatency
    expr: |
      avg_over_time(
        network_ping_rtt_ms{src="home",dst="cloud"}[5m]
      ) > 150
    for: 5m
    labels:
      severity: warning
    annotations:
      summary: "家→云网络延迟过高"
      description: "平均RTT {{ $value }}ms，超过150ms阈值"
```

### 11.3 备份恢复

#### 11.3.1 数据库备份

**自动备份脚本**（`scripts/db_backup.sh`）：
```bash
#!/bin/bash
set -e

BACKUP_DIR="/backups/postgres"
TIMESTAMP=$(date +%Y%m%d_%H%M%S)
BACKUP_FILE="$BACKUP_DIR/naicha_$TIMESTAMP.dump"

# 创建备份目录
mkdir -p $BACKUP_DIR

# 执行备份
pg_dump -h $DB_HOST -U $DB_USER -d naicha \
  --format=custom \
  --compress=9 \
  --file=$BACKUP_FILE

# 保留最近30天的备份
find $BACKUP_DIR -name "naicha_*.dump" -mtime +30 -delete

echo "Backup completed: $BACKUP_FILE"
```

**CronJob配置**：
```yaml
# backup-cronjob.yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: postgres-backup
  namespace: naicha-prod
spec:
  schedule: "0 2 * * *"  # 每天凌晨2点
  jobTemplate:
    spec:
      template:
        spec:
          containers:
          - name: backup
            image: postgres:14-alpine
            command:
            - /bin/sh
            - -c
            - |
              pg_dump -h postgres -U $DB_USER -d naicha \
                --format=custom --compress=9 \
                --file=/backups/naicha_$(date +\%Y\%m\%d_\%H\%M\%S).dump
            env:
            - name: DB_USER
              valueFrom:
                secretKeyRef:
                  name: naicha-api-secrets
                  key: DB_USER
            - name: PGPASSWORD
              valueFrom:
                secretKeyRef:
                  name: naicha-api-secrets
                  key: DB_PASSWORD
            volumeMounts:
            - name: backups
              mountPath: /backups
          volumes:
          - name: backups
            persistentVolumeClaim:
              claimName: postgres-backup-pvc
          restartPolicy: OnFailure
```

#### 11.3.2 数据库恢复

```bash
# 1. 停止API服务（避免写入）
kubectl scale deployment naicha-api -n naicha-prod --replicas=0

# 2. 创建恢复点备份（保险起见）
pg_dump -h $DB_HOST -U $DB_USER -d naicha \
  --format=custom \
  --file=/backups/before_restore_$(date +%Y%m%d_%H%M%S).dump

# 3. 执行恢复
pg_restore -h $DB_HOST -U $DB_USER -d naicha \
  --clean --if-exists \
  /backups/naicha_20251110_020000.dump

# 4. 重启API服务
kubectl scale deployment naicha-api -n naicha-prod --replicas=2

# 5. 验证数据完整性
python scripts/verify_data_integrity.py
```

### 12.3 常见问题FAQ

**Q1: 如何添加新的支付渠道？**

A: 参考`app/services/payments.py`，实现以下步骤：
1. 在`payment_records.channel`枚举中添加新渠道
2. 实现渠道专用的支付初始化方法
3. 实现回调处理逻辑
4. 添加集成测试
5. 更新`doc/api.md`文档

**Q2: 如何配置定时任务的执行时间？**

A: 修改`app/workers/tasks.py`中的`celery_app.conf.beat_schedule`：
```python
"daily-reconciliation": {
    "task": "app.workers.tasks.run_daily_reconciliation",
    "schedule": crontab(hour=3, minute=0),  # 修改为3:00执行
}
```

**Q3: 如何处理大量历史订单导致的性能问题？**

A: 采用以下策略：
1. **分表归档**：将1年前的订单迁移到历史表
2. **索引优化**：为常用查询条件创建覆盖索引
3. **缓存预热**：对热点订单状态进行Redis缓存
4. **分页优化**：使用游标分页替代offset分页

**Q4: 如何实现灰度发布？**

A: K8s环境推荐使用Canary部署：
```bash
# 1. 创建Canary Deployment（1个副本，新版本）
kubectl apply -f api-deployment-canary.yaml

# 2. 配置流量分割（90%旧版本，10%新版本）
kubectl apply -f api-service-canary.yaml

# 3. 观察指标，逐步增加新版本流量
# 4. 全部切换后删除旧版本
```

**Q5: 数据库备份文件太大，如何优化？**

A: 采用增量备份策略：
1. 每周一次全量备份
2. 每天一次增量备份（WAL归档）
3. 使用`pg_basebackup`实现在线备份
4. 备份文件压缩后上传到对象存储
